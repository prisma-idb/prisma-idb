## Post-Phase-7 architectural notes

These complement the per-ADR records and capture decisions made during Phase 7 that don't yet have a dedicated ADR:

- **The CLI has no driver path for IDB.** `executeAcrossSpaces` returns a `IDB-CLI-UNSUPPORTED` envelope; `verify` / `sign` / `readMarker` / `introspect` on the family instance return refusal envelopes or null. The framework SPI still requires a `driver:` value in `prisma.config.ts` — use the stub `@prisma-idb/driver-idb/control` default export.

- **Authoring → bundling → applying are three separate stages.** Author with `prisma-next migration new` (writes to disk). Bundle with `prisma-idb migration contract-space` (assembles ContractSpace). Apply with `createAutoMigratingIdbClient` (browser). Validation gate is `prisma-idb migration preflight`.

- **`fake-indexeddb` lives in exactly one production code path**: `family-idb/core/preflight.ts`, the standalone preflight command. Everywhere else (runtime, browser, CLI authoring) uses real IndexedDB or trusts the bundled `ops.json` blobs.

- **The control SPI has no "unsupported" discriminator for browser-only targets.** `introspect`/`readMarker`/`readAllMarkers` have concrete return types with no way to signal "this cannot run in this environment" short of `null`/empty + a refusal envelope from `verify`/`sign`. Flagged upstream to Will Madden (2026-06-04) as worth a framework PR adding a proper discriminator; not blocking, current workaround (null/empty + refusal envelopes) stands until that lands.

## Sync architecture (ADRs 012-014)

ADRs 012-014 are a related group, drafted 2026-08-06 in response to open questions raised in the Discord thread with Will Madden (schema scoping, runtime-plane separation, migration-lifecycle coordination — 2026-06-10/11) and the user's own review of the pull/push implementation. All three are implemented (013 and 014 on 2026-08-07 and 2026-08-09 respectively) — read them together; each depends on the one(s) before it:

```
ADR 012 (contract subsetting)
   └─ ADR 013 (FK projection — depends on 012's excluded-model set)
         └─ ADR 014 (ownership DAG — needs root-model reachability over 013's survivor set)
```

Two things Will's answers ruled out that are worth stating explicitly so they aren't re-litigated: a single unified client/server ORM (rejected — "no point exposing DB elements to the browser which it can't access"), and reusing `model.owner` for sync authorization (rejected in ADR 014 — it's a storage-locality fact, not an authorization fact). One question from that thread remains genuinely open and isn't addressed by ADRs 012-014: the shape of the `withoutTracking`/local-only-write opt-out on `sync-extension-idb` (asked 2026-08-01, no framework-idiomatic answer received yet).

A follow-up validation ADR and a migrations record-transform ADR are drafted but not yet decided — tracked outside this index until reviewed.
