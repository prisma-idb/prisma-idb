# Phase 8.5 — CLI/config unification (`prisma.config.ts` rename)

Stack layer: `feat/prisma-8` → `phase-8.2-content-hash` → `phase-8.3-contract-layer` → `phase-8.4-runtime-core-split` → `phase-8.5-cli-config-unification`. Depends on 8.1 and 8.3 per `PLAN_8.0` §9.

## 0. What `PLAN_8.0`'s phase table actually asked for, and why the real scope is much narrower

§9's row for 8.5 says: rename both example apps' `prisma-next.config.ts` → `prisma.config.ts` with the `definePrismaConfig({ orm: … })` envelope, add `@prisma/cli-engine` (exact `0.2.0`), and — once `contract emit` works against rc.4-shaped config — re-emit every Tier-1 contract (deferred from 8.3, per `PLAN_8.3` §0). Doing this required answering a question §5.3 left open ("whether `definePrismaConfig`'s single recognized-sections model means our own `idbCommandFamily` needs its own `configSection`") and turned up two findings big enough to reshape the phase.

**Finding 1 — the generic `prisma` CLI already handles our IDB-family config, no `idbCommandFamily` needed.** Read `@prisma/orm-framework/config/config-types`'s installed `.d.mts` directly: its `defineConfig` — already re-exported by `family-idb/src/exports/config-types.ts` as `coreDefineConfig`, unchanged since before this port — carries the doc comment _"Builds the ORM section of `prisma.config.ts`. The result nests under the `orm` key of the engine's `defineConfig` — the marker lives on the envelope, not here."_ It's generic over `TFamilyId`/`TTargetId`, not SQL-specific. Confirmed empirically, not just from the type: wrapped `apps/prisma-orm-usage`'s existing IDB config (`family: idbFamily, target: idbTarget, adapter: idbAdapter, driver: idbDriver, …`) in a throwaway `definePrismaConfig({ orm: … })` envelope and ran the real, published `prisma@8.0.0-rc.7` binary's `contract emit` against it — it worked, emitting a real `contract.json`/`contract.d.ts` with computed hashes. `ormCommandFamily`'s generic commands (`contract emit`, `db verify`, etc.) don't care which family populates the `orm` section; only our own IDB-specific commands (`migration plan`/`migration contract-space`/`migration preflight`) need a bespoke command family, and that's still genuinely Phase 8.6's job (§7 decision 2).

**Finding 2 — re-emission moves `storageHash`/`profileHash`, contradicting `PLAN_8.3` §3 item 3's "hash-inert" prediction, and every Tier-1 package except one has a committed migration chain that depends on the old value.** Comparing the experiment's freshly-emitted contract against the currently-committed one: `storage.stores`/`namespaces` and `capabilities` were byte-identical, `extensionPacks`→`extensions` (both `{}`) was the only visible key change — yet `storageHash` and `profileHash` both moved (`e8f91dc…`→`fc8ba56…`, `e97a15c…`→`4032983…`). `computeStorageHash`'s actual inputs (`target`, `targetFamily`, `storage` — read directly in `family-idb/src/core/contract-builder.ts`) were verified identical between the two runs, so the change isn't in our code or the schema; it's in the vendor's `computeStorageHash`/`computeProfileHash` implementation (`@prisma/orm-framework/contract/hashing`) somewhere between whatever built the frozen-0.16.0-era contract and rc.4's version. This is measured, not derived from reading that implementation — the mechanism is unconfirmed, only that the output changed for identical input.

That matters because `storageHash` is load-bearing at runtime, not just an artifact label: `IdbRuntimeImpl.verifyMarker()` (`runtime-idb/src/idb-runtime.ts`) compares a persisted marker's `storageHash` against the current contract's; `auto-migrate.ts` and `family-idb/src/core/migration-plan.ts` both hard-error on a chain whose `end-contract.json` doesn't match. Grepping for the old contract's hash value across every Tier-1 package's tree found it baked into a _committed_ `end-contract.json` everywhere except one place:

| Package/app                                      | Committed migration chain?                                                                                                                                                             | Contract re-emission safe now? |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------ |
| `apps/prisma-orm-usage` (IDB)                    | Yes — `migrations/app/20260621T1214_add_tag/end-contract.json`                                                                                                                         | No                             |
| `apps/prisma-idb-kanban-example` (IDB side)      | Yes — `migrations/app/20260621T1057_baseline/end-contract.json`                                                                                                                        | No                             |
| `apps/prisma-idb-kanban-example` (Postgres side) | Yes — `migrations-postgres/app/*/end-contract.json`                                                                                                                                    | No (also Tier 2, see below)    |
| `sync-extension-idb`                             | Yes — `migrations/20260802T0712_install_sync_extension/end-contract.json`                                                                                                              | No                             |
| `sync-server-sql`                                | **No** — `test/fixtures/migrations-postgres/` is `.gitignore`d (`# Bootstrap-only ("db init", never authored migrations) — fully derived per-environment state, not portable history`) | **Yes**                        |

Re-emitting any of the four "No" rows today would produce a `contract.json` whose hash no longer matches its own package's last migration's `end-contract.json` — the exact `MIGRATION.CONTRACT_SPACE_VIOLATION` class of error `family-idb/src/core/migration-plan.ts` (lines 241/251) exists to catch. Fixing that for real needs the whole chain regenerated via `migration plan`/`migration contract-space` — our own commands, which don't exist as working CLI surface until Phase 8.6 mounts `idbCommandFamily`. Renaming those four configs now, without anything able to safely regenerate their chains, buys nothing: `family-idb`'s own bin (`bin/prisma-next-idb.ts`, `core/resolve-cli-paths.ts`) still hardcodes `prisma-next.config.ts` as its default-discovery filename and is being replaced wholesale in 8.6 anyway, and the generic `prisma` CLI can't be safely run against them until the chain-regeneration problem is solved.

**Kanban's Postgres side is a second, independent reason to leave it alone**: it's Tier 2 (`PLAN_8.0` §7 decision 4 — "DEFERRED, still open... needs its own scoped survey before anyone starts it"), not merely deferred to 8.6. Its `package.json` still carries `@prisma-next/family-sql`, `@prisma-next/migration-tools`, `@prisma-next/postgres`, `@prisma-next/sql-builder`, `@prisma-next/sql-contract`, all at the frozen `^0.16.0` — and `src/lib/server/db.ts`/`auth.ts` import from `@prisma-next/postgres` directly, not just the config file. This is a whole unsurveyed tier, not a stray Phase 8.1 leftover — confirmed by checking the actual dependency block and every real importer, not just the one config-file import line that first looked like an oversight.

Asked the user directly how to handle kanban's `"build": "pnpm contract:emit:postgres && vite build"` script, since repointing it at the real `prisma` bin would make it _succeed_ while silently producing a chain-inconsistent contract (worse than today's loud dead-CLI failure). Decision: leave kanban's Postgres scripts entirely un-rewired in this phase — consistent with the Tier-2 finding above.

## 1. What this phase actually does

Only `packages/prisma-orm/sync-server-sql` gets the full treatment — it's the one package where every part of §9's row is both safe and independently verifiable:

1. **`prisma-next.config.ts` → `prisma.config.ts`**, wrapped in the envelope:
   ```ts
   import { definePrismaConfig } from "@prisma/cli-engine";
   import { defineConfig as ormConfig } from "@prisma/orm-postgres/config";
   // …
   export default definePrismaConfig({
     orm: ormConfig({ contract: …, db: …, migrations: … }),
   });
   ```
   Used `definePrismaConfig`, not the deprecated `defineConfig` alias `@prisma/cli-engine@0.2.0` also exports (confirmed via its `.d.ts`: `/** @deprecated Renamed to {@link definePrismaConfig} */ declare const defineConfig: typeof definePrismaConfig;`) — vendor's own `prisma-8-demo` example still imports the deprecated `defineConfig` name, which is presumably why `PLAN_8.0` §5.2 wrote the envelope that way too. Worth naming so a future session doesn't "fix" this back to match that example.
2. **`package.json`**: removed the `prisma-next: ^0.16.0` devDependency (the dead CLI bin); added `@prisma/cli-engine: 0.2.0` and `prisma: 8.0.0-rc.7` (exact) as devDependencies. `prisma@rc.7` is a deliberate bridge dependency — §5.2 floats mounting `ormCommandFamily` inside our own `@prisma/cli-engine`-based shell later, which could let Phase 8.6 drop this dependency again. Not an accident to leave unexplained.
3. **Scripts rewired** to the real binary: `contract:emit:postgres`: `prisma-next contract emit --config prisma-next.config.ts` → `prisma contract emit --config prisma.config.ts`; `db:init`: `prisma-next db init --config prisma-next.config.ts` → `prisma db init --config prisma.config.ts`.
4. **Actually ran the re-emission** (safe here — no committed chain to invalidate): `pnpm contract:emit:postgres` now succeeds, producing the same gitignored `test/fixtures/schema.generated.{json,d.ts}` this package always regenerates fresh.
5. **`pnpm-workspace.yaml`**: adding `prisma@rc.7` pulls in `@prisma/composer-cli`'s dependency tree (`alchemy`, Cloudflare Workers tooling), which transitively depends on `msgpackr-extract`/`workerd` — packages with native install scripts pnpm's `allowBuilds` gate hadn't been asked about yet. Once added (as `false` — declining to run either; we don't need Cloudflare Workers tooling for anything), _any_ script in the whole workspace ran cleanly again; before that, even an unrelated package's `pnpm run lint` failed with the same `pnpm.mjs install` internal error, which is what flagged this as environment-wide rather than sync-server-sql-specific.

**Not touched, and why:**

- `apps/prisma-orm-usage`, `apps/prisma-idb-kanban-example`'s IDB-side config, `sync-extension-idb` — all have committed migration chains that a re-emission would invalidate, and their only real consumer (`family-idb`'s own bin) is being replaced wholesale in Phase 8.6, so renaming now serves no working tool. Bundle these renames with 8.6's chain-regeneration + `idbCommandFamily` work.
- `apps/prisma-idb-kanban-example/prisma-next.config.postgres.ts` and everything else on that app's Postgres side — Tier 2, `PLAN_8.0` §7 decision 4, unscoped Phase 8.8. Not this phase's, not 8.6's either.

## 2. Environment side-quest: a stale gitignored fixture

Running `sync-server-sql`'s `pnpm test` for real the first time hit `MIGRATION.CONTRACT_SPACE_VIOLATION: Ref "db" for contract space "app" is unreadable` from `prisma db init`. Cause: `test/fixtures/migrations-postgres/app/refs/db.json` — fully gitignored, untracked, left over from some earlier run in this working tree — pointed at a contract hash with no corresponding migration package actually on disk. Deleted the whole gitignored directory (exactly what its own `.gitignore` comment says it's for: "fully derived per-environment state, not portable history") and re-ran; `db init` created a fresh baseline and the suite passed. Not a code fix — a local-environment cleanup, noted here in case a future session hits the same confusing error and wonders whether it's a real regression.

## 3. Validation

- `pnpm install` (repo root): clean, after the `allowBuilds` fix above.
- `sync-server-sql`: `pnpm run contract:emit:postgres` — succeeds (`ok: true`, contract emitted). `pnpm run check` (`contract:emit:postgres && tsc --noEmit`) — exit 0. `pnpm run test` (`contract:emit:postgres && db:create && db:init && vitest run`, against a real Postgres via `.devcontainer/docker-compose.yml`'s `db` service) — **23/23 passing**, up from the `PN-CLI-4009` dead-CLI failure `PLAN_8.4` §4 documented as this package's pre-existing baseline. This is the phase's one concrete, verifiable claim: a previously-broken Tier-1 suite is green again, via the repo's own scripts, not a workaround.
- `cli-tests`: untouched by this phase and unchanged — **23 failed / 9 passed of 32**, identical to the documented baseline. Its failures are `family-idb`'s own `resolve-cli-paths.ts` default-discovery convention hitting the dead bin/old filename (see §4) — Phase 8.6's territory, not something 8.5 was ever going to fix.
- `client-idb`: unaffected — verified via a standalone `pnpm build` after a `turbo run test --filter=…` pass reported it failing; that failure didn't reproduce standalone, consistent with turbo cancelling sibling tasks after `cli-tests` failed rather than an actual regression from this phase's changes (this phase touches nothing in `client-idb`).
- Repo-wide `pnpm --filter "./packages/prisma-orm/*" build`: green.
- No changes to `apps/prisma-orm-usage`/`apps/prisma-idb-kanban-example`/`sync-extension-idb` in this phase, so their own build/check/test status is exactly what `PLAN_8.4` §4 already recorded.

## 4. Guidance for future sessions (Phase 8.6 and beyond)

- **Phase 8.6 owns, together**: mounting `idbCommandFamily` (`migration plan`/`contract-space`/`preflight`) via `createCli`, regenerating the four committed migration chains this phase left alone (`prisma-next-usage`, kanban's IDB side, `sync-extension-idb`, and — separately — kanban's Postgres side once Tier 2 gets its own survey), and _then_ renaming those four configs to `prisma.config.ts` with the envelope, matching this phase's pattern. Doing the rename before the chain regeneration is possible (it's a static rewrite) but pointless until something can safely consume it.
- **The hash-algorithm change is real and unexplained** — `computeStorageHash`/`computeProfileHash`'s inputs matched exactly, outputs didn't. Whoever regenerates a chain in 8.6 should expect every `end-contract.json` in the chain to get a new hash, not just the newest one — re-running `db init`/`verifyMarker` against a live database that has an old-hash marker persisted (a real end user's browser, for a generated app) will read as a schema mismatch requiring a fresh migration story, not a silent no-op. Worth deciding deliberately (e.g. a documented "cross this once" migration note for generator consumers) rather than discovering it from a bug report.
- **`family-idb`'s own bin/`resolve-cli-paths.ts` hardcodes `prisma-next.config.ts` as its default-discovery filename** — this needs to change as part of 8.6's `idbCommandFamily` work regardless of the chain-regeneration timing, since it's literally the thing being replaced.
- `prisma@8.0.0-rc.7` in `sync-server-sql`'s devDependencies is a deliberate bridge, not a typo to "fix" toward `@prisma/orm-toolchain` or similar — see §1 item 2.
- Don't "fix" the `definePrismaConfig` import back to the deprecated `defineConfig` alias to match vendor's own example — see §1 item 1.
