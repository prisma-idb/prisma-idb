When a pulled delete or ownership revocation cascades to rows with unsent local edits, those edits are now discarded in the same transaction: their outbox events are marked non-retryable, and the rows no longer count as pending. Before, the cascade removed the rows but left their edits queued, so the outbox disagreed with the local data and a later push failed or reconciled over a change the user could no longer see. An unsent edit that moved a row onto the deleted parent stays queued, with the row's other unsent edits, because the server still has the row under its old parent; its push is rejected and reconciliation restores the row. The move is recognized through whatever fields the relation references, such as a unique field, a compound key or a `Decimal` key in another spelling. The docs now describe how to inspect, recover and delete discarded events, which the worker's cleanup keeps. Checking the cascaded rows of a model with a `Decimal` key reads the sync version metadata once per pulled delete, not once per row. A discard announces `outboxchange`, since the pending count changed. To tell a move from an update that only repeats the row's parent, a tracked update whose patch lists a foreign key now reads the row first and keeps the key's old value in the event's `payload.previous`, which servers ignore.
