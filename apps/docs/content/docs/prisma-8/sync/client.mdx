Reference for `@prisma-idb/sync-extension-idb`. To set it up, follow the [Sync tutorial](/docs/prisma-8/sync).

## Opening a sync client

All three functions come from `@prisma-idb/sync-extension-idb/client`.

| Function                                    | Use it when                                                                                                                                                           |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `createManagedAutoSyncIdbClient(options)`   | Most apps. A shared client with `get()`, `close()` and `reset()`, like [`createManagedAutoIdbClient`](/docs/prisma-8/client#share-one-client-and-reset-it-on-logout). |
| `createAutoMigratingSyncIdbClient(options)` | You manage the client's lifetime yourself. Migrates, then returns a sync client.                                                                                      |
| `createSyncIdbClient({ contract, dbName })` | The database is already migrated.                                                                                                                                     |

The options are the same as `createAutoMigratingIdbClient`'s, plus `trackedModels`: an array of model names to record for sync, or `"*"` for every model, the default. Writes to other models stay local. Include `idbSyncExtension` from `@prisma-idb/sync-extension-idb/control` in `extensions`, so the database gets the sync stores, `_idb_sync_outbox` and `_idb_sync_version_meta`.

## Client members

| Member                            | Description                                                                                      |
| --------------------------------- | ------------------------------------------------------------------------------------------------ |
| `db.orm`                          | The same API as a plain client. Every write is also recorded for sync.                           |
| `db.withoutTracking(fn)`          | Runs `fn(orm)` with writes that aren't recorded, so they never sync.                             |
| `db.on("outboxwrite", cb)`        | Calls `cb` after each write commits, with the recorded changes. Returns an unsubscribe function. |
| `db.createSyncWorker(opts)`       | Creates a [sync worker](#sync-worker) for this client.                                           |
| `db.rawClient`                    | The underlying plain client. Writes through it aren't recorded.                                  |
| `db.verifyMarker()`, `db.close()` | Same as on a plain client.                                                                       |

## The outbox

Every write through `db.orm` also writes an event to the outbox store, in the same transaction. The two commit together or not at all, so no change is ever lost or sent without being saved.

`"outboxwrite"` fires once per write call, after it commits: once for a `create()`, and once with every change for a `createAll()`, `updateAll()` or a delete that cascades. It never fires for a write that rolled back.

```ts
const unsubscribe = db.on("outboxwrite", (entries) => {
  // entries: readonly { modelName, operation, key, payload }[]
});
```

Use `withoutTracking` for writes the server shouldn't receive, such as local-only drafts, or a copy of a row that came from the server:

```ts
await db.withoutTracking((orm) => orm.user.upsert({ where: { id }, create: user, update: user }));
```

## Conflicts

For each synced record, `_idb_sync_version_meta` records two things:

- **Whether a local change is waiting to be pushed.** While one is, pulls skip that record, so a local change is never overwritten before it reaches the server.
- **The last changelog id applied to it.** A pull that isn't newer is skipped, so a repeated or out-of-order pull can't undo a newer change.

The worker maintains this store; you don't write to it.

## Sync worker

```ts
const worker = db.createSyncWorker({ pushHandler, pullHandler });
worker.start();
```

The worker doesn't start on its own. Each cycle pushes a batch of outbox events, then pulls. It repeats every `intervalMs` while idle, and backs off after failures.

| Option             | Default  | Description                                                                                                                          |
| ------------------ | -------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `pushHandler`      | Required | `(events, signal) => Promise<PushResult[]>`. Sends events to your push endpoint.                                                     |
| `pullHandler`      | Required | `(fromChangelogId, signal) => Promise<LogWithRecord[]>`. Fetches changes after `fromChangelogId`, which is `null` on the first pull. |
| `batchSize`        | `20`     | Outbox events pushed per cycle.                                                                                                      |
| `intervalMs`       | `5000`   | Time between cycles while idle.                                                                                                      |
| `backoffBaseMs`    | `1000`   | Wait after the first failed cycle. Doubles with each failure in a row.                                                               |
| `backoffMaxMs`     | `30000`  | The longest wait between failed cycles.                                                                                              |
| `requestTimeoutMs` | `30000`  | Aborts a handler call through its `signal` after this long.                                                                          |

| Method or property | Description                                                                                              |
| ------------------ | -------------------------------------------------------------------------------------------------------- |
| `start()`          | Starts the loop. Does nothing if it's running.                                                           |
| `stop()`           | Lets the current cycle finish, then stops.                                                               |
| `forceSync()`      | Runs a cycle now, ignoring any backoff.                                                                  |
| `status`           | `"idle"`, `"pushing"`, `"pulling"`, `"error"` or `"stopped"`.                                            |
| `on(event, cb)`    | Subscribes to `"statuschange"`, `"pushcompleted"` or `"pullcompleted"`. Returns an unsubscribe function. |

Most apps also call `forceSync()` on the browser's `online` event, and `stop()` on sign-out.

The push and pull response shapes are exported as Zod schemas from `@prisma-idb/sync-extension-idb/schemas`: `pushResultSchema` and `logWithRecordSchema`.
