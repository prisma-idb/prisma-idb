This page shows how to open the client in common situations. For a first setup, follow the [Quick Start](/docs/prisma-8/getting-started).

## Open the database

`createAutoMigratingIdbClient` opens the database, applies any pending migrations, and resolves to a client. Cache the promise so the database opens once:

```ts
import { createAutoMigratingIdbClient } from "@prisma-idb/client-idb/client-auto";
import type { IdbClient } from "@prisma-idb/client-idb/client-auto";
import type { Contract } from "./prisma/contract";
import { contractSpace } from "./prisma/contract-space.generated";

let db: Promise<IdbClient<Contract>> | null = null;

export function getDb(): Promise<IdbClient<Contract>> {
  return (db ??= createAutoMigratingIdbClient({ contractSpace, dbName: "my-app" }));
}
```

`dbName` is the IndexedDB database name. Use a different name to keep separate databases in the same browser, for example one per tenant.

The client applies every pending migration as it was planned, including ones that delete data. Review those when you plan them; see [Destructive changes](/docs/prisma-8/migrations#destructive-changes).

## Use schema enums

Every client exposes Prisma 8's runtime enum accessors under `db.enums`, keyed by domain namespace and enum name. For a PSL schema without an explicit namespace, use `__unbound__`:

```ts
const Role = db.enums.__unbound__.Role;
const role: typeof Role.Value = Role.members.ADMIN;
const roles = Role.values; // ["USER", "ADMIN"] for those declared members

if (Role.has(input)) {
  // input is narrowed to the enum's value union
}
```

`members` maps member names to application values, including explicit stored strings. `names`, `hasName`, `nameOf`, and `ordinalOf` are also available. `Value` is type-only: use `typeof Role.Value` in type positions. Existing field types and string-literal usage keep working. Auto-migrating and sync clients expose the same API; sync clients share it with `db.rawClient.enums`.

Accessors come from the emitted contract, so regenerate it after changing enums. With a client projection, only the enums retained in the client contract are available.

## Share one client and reset it on logout

`createManagedAutoIdbClient` wraps the same options in a singleton with a safe `reset()`. Use it when the app needs to wipe local data, for example so a different account signing in on the same browser never sees the previous user's rows.

```ts
import { createManagedAutoIdbClient } from "@prisma-idb/client-idb/client-auto";

const managedDb = createManagedAutoIdbClient({ contractSpace, dbName: "my-app" });

export const enums = managedDb.enums; // available before opening IndexedDB
export const getDb = () => managedDb.get();
export const closeDb = () => managedDb.close();
export const resetDb = () => managedDb.reset(); // call on sign-out
```

| Method    | Does                                                                                                          |
| --------- | ------------------------------------------------------------------------------------------------------------- |
| `get()`   | Opens the database on the first call and returns the same client after that. Concurrent calls share one open. |
| `close()` | Closes the client, if one is open.                                                                            |
| `reset()` | Closes the client and deletes the database.                                                                   |

`managedDb.enums` has the same type and values as the opened client's `enums`. Reading it does not open IndexedDB, so it also works during server rendering.

`reset()` is safe to call at any time. It waits for an open that's in progress before deleting, and a `get()` called during a reset waits for the delete to finish, then opens a fresh database.

Using sync? Use `createManagedAutoSyncIdbClient` from `@prisma-idb/sync-extension-idb/client` instead. It works the same way. See [Sync](/docs/prisma-8/sync).

### Wrap a different factory

`createManagedAutoIdbClient` is `createManagedIdbClient` with the factory already chosen. To wrap something else, such as `createIdbClient` on a database you migrate yourself, use `createManagedIdbClient`:

```ts
import { createIdbClient, createManagedIdbClient } from "@prisma-idb/client-idb/client";
import { createIdbEnums } from "@prisma-idb/client-idb/internal";

const managedDb = createManagedIdbClient(async () => createIdbClient({ contract, dbName: "my-app" }), {
  enums: createIdbEnums(contract), // must use the factory's contract
  dbName: "my-app", // must match the factory's dbName
});
```

`createIdbClient` returns a client synchronously. The `async` factory above adapts it to the promise-returning factory required by `createManagedIdbClient`.

`createManagedIdbClient` only uses its own `dbName` to delete the database in `reset()`. Nothing checks that it matches the factory's. If they differ, `get()` still opens the right database, but `reset()` deletes a different one and your data stays. Prefer `createManagedAutoIdbClient` unless you need a custom factory.

## Add an extension

An extension adds its own object stores and ships its own migrations. Pass it in `extensions`, and its migrations run together with yours when the database opens:

```ts
import { createAutoMigratingIdbClient } from "@prisma-idb/client-idb/client-auto";
import { idbSyncExtension } from "@prisma-idb/sync-extension-idb/control";

const db = await createAutoMigratingIdbClient({
  contractSpace,
  dbName: "my-app",
  extensions: [idbSyncExtension],
});
```

You don't plan or edit an extension's migrations. The sync extension is currently the only one; see [Sync](/docs/prisma-8/sync).

## Add middleware

Pass `middleware` to `createIdbClient`, `createAutoMigratingIdbClient` or a sync client to observe or change statements, for example to log or cache them. A middleware sees top-level queries with every hook, and the statements inside transactions with fewer guarantees:

```ts
import type { IdbMiddleware } from "@prisma-idb/runtime-idb/runtime";

const logger: IdbMiddleware = {
  name: "logger",
  familyId: "idb",
  async activityFinalized(activity, result, ctx) {
    if (activity.kind === "statement") console.log(ctx.scope, result.outcome);
  },
};

const db = await createAutoMigratingIdbClient({ contractSpace, dbName: "my-app", middleware: [logger] });
```

Inside a transaction, which covers `db.transaction()` and the nested, cascading and foreign-key-checked parts of a write:

- Each statement is an activity beneath a transaction activity, and `ctx.scope` is `"transaction"`.
- The statement hooks `activityStarted`, `beforeEncode`, `onRow` and `activityEnded` are called but not awaited. IndexedDB commits a transaction that waits, so a hook that awaits would end it early. Only the synchronous part of a hook runs before the statement, so don't change a plan after an `await` in `beforeEncode`. The first time an async `beforeEncode` runs in a transaction, you get an `IDB.MIDDLEWARE_ASYNC_IN_TRANSACTION` warning.
- `intercept` hooks are not called, so a cache never serves a read inside a transaction.
- When the transaction completes or aborts, every statement and then the transaction get `activityFinalized` with `committed`, `rolled-back` or `unknown`. `commit()` resolves after those hooks, so invalidate a cache there.
- A hook's error is logged and never fails the statement or the transaction. The one exception is an error from the transaction's own `activityStarted`, which rejects before the transaction opens. The client's logger writes warnings and errors to the console.

## Client reference

| Member                           | Description                                                                                   |
| -------------------------------- | --------------------------------------------------------------------------------------------- |
| `db.enums`                       | Runtime enum accessors keyed by domain namespace and enum name.                               |
| `db.orm`                         | One accessor per model, such as `db.orm.todo`. See [API](/docs/prisma-8/api).                 |
| `db.verifyMarker()`              | Resolves to `true` when the database's schema matches the contract.                           |
| `db.withTransaction(stores, fn)` | Runs low-level plans in one transaction. See [Transactions](/docs/prisma-8/api/transactions). |
| `db.close()`                     | Closes the connection.                                                                        |

The runtime checks the app contract marker on the first database query or transaction on each connection. A query served by middleware without touching IndexedDB leaves the check for the next database use. A missing marker logs `CONTRACT.MARKER_MISSING`, and a different marker logs `CONTRACT.MARKER_MISMATCH`. An unreadable marker logs `CONTRACT.MARKER_UNREADABLE`. The warning itself allows the operation to proceed. If an upgrade closes the connection, the driver only reconnects when the contract markers that were already present still match. Auto-migrating clients write the app marker before opening. Pass `verifyMarker: false` to `createIdbClient` or `createSyncIdbClient` to skip the warning check. The runtime warning compares only the `app` marker.
